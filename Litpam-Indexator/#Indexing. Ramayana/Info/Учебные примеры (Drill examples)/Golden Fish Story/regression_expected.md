# Регрессионный дрилл: дефект «одной формы» — эталон-снимок

_Created: 08-07-2026 · Last updated: 08-07-2026_

Эталон для регрессионной проверки [`UseReadyTable.v.7.jsx`](https://github.com/gasyoun/RussianRamayana/blob/main/Litpam-Indexator/%23Indexing.%20Ramayana/%5B1.%20%D0%9F%D0%BE%D0%B4%D0%B3%D0%BE%D1%82%D0%BE%D0%B2%D0%BA%D0%B0%20%D1%82%D0%B0%D0%B1%D0%BB%D0%B8%D1%86%5D)
на дефекте «одной формы» (слово «ними», видео
[15](https://www.youtube.com/watch?v=wK60yNgeEqA&t=213s) → исправлено, видео
[18](https://www.youtube.com/watch?v=dtuew2WHt64&t=1s)). Процедура запуска и назначение —
в [`MANUAL.md` § «Регрессионный дрилл (Golden Fish)»](https://github.com/gasyoun/RussianRamayana/blob/main/Litpam-Indexator/docs/indesign-pipeline/MANUAL.md#регрессионный-дрилл-golden-fish).

## Зачем

Дефект «одной формы» **тихий**: скрипт не падает, но при термине с *единственной* падежной
формой строит неверный grep-запрос, который потом просто ничего не находит — и это всплывает
только в `log.txt` после ≈1,5-часового индексирования реального тома. Дрилл ловит регресс за
секунды на маленьком контролируемом входе.

## Минимальный вход (строки-ловушки)

Добавить к стартовому `IndexList` учебного примера
[`Golden Fish.idml`](https://github.com/gasyoun/RussianRamayana/blob/main/Litpam-Indexator/%23Indexing.%20Ramayana/Info/%D0%A3%D1%87%D0%B5%D0%B1%D0%BD%D1%8B%D0%B5%20%D0%BF%D1%80%D0%B8%D0%BC%D0%B5%D1%80%D1%8B%20(Drill%20examples)/Golden%20Fish%20Story/Golden%20Fish.idml)
эти строки (колонка 1 — термин, колонка 2 — падежные формы). Ключевое условие ловушки —
**ровно одна форма** в колонке 2 (именно этот случай ломался):

| # | Термин (колонка 1) | Формы через `;` (колонка 2) | Чем проверяет |
|---|---|---|---|
| L1 | `ними` | `ними` | базовый случай «одна форма», ≥4 знаков (declension-путь `simpleSearch=false`) — тот самый регресс |
| L2 | `кха-тха` | `кха-тха` | одна форма с дефисом (grep-поиск пропускает мягкий перенос после дефиса — см. комментарий 11.11.2020 в `ForIndex.jsxinc`) |
| L3 | `ом` | `ом` | одна форма < 4 знаков (короткое слово → ветка `we + curWord + we`) |
| L4 | `супруг` | `супруг; супруга; супруги` | контроль: **несколько** форм, сортировка по убыванию длины — не должно затрагиваться правкой |

## Ожидаемый выход (свойства запроса)

После прогона `UseReadyTable.v.7.jsx` в третьей колонке `IndexList` для каждой строки-ловушки
должен получиться grep-запрос, удовлетворяющий свойствам ниже. Свойства выведены из кодового
контракта [`ForIndex.jsxinc`](https://github.com/gasyoun/RussianRamayana/blob/main/Litpam-Indexator/%23Indexing.%20Ramayana/ForIndex.jsxinc)
(`we = "\b"`, строка 67; ветки построения запроса, строки ~380–405):

- **L1 `ними`** — запрос должен **содержать саму форму `ними`** и обрамляться границами слова
  (`\b…\b`); он обязан реально находить «ними» в тексте. Регресс дефекта = запрос, который
  формы `ними` **не** содержит или не матчит её (пустой результат в `ShowFoundByGrep`).
- **L2 `кха-тха`** — дефис сохранён; между частями допускается опциональный мягкий перенос
  (в коде — `defis + sepSpace + "*"`, ныне отключён, поэтому достаточно буквального дефиса).
  Запрос находит «кха-тха» в тексте.
- **L3 `ом`** — короткое слово: запрос ровно `\bом\b` (ветка `curWordLength < 4`).
- **L4 `супруг…`** — три формы, отсортированные **по убыванию длины** (`супруги`/`супруга`
  раньше `супруг`), объединённые в один запрос; каждая обрамлена границей слова.

Общее для всех: регистр управляется префиксом `-I`/`-i` (см.
[`MANUAL.md` § «Логика UseReadyTable.v.7.jsx»](https://github.com/gasyoun/RussianRamayana/blob/main/Litpam-Indexator/docs/indesign-pipeline/MANUAL.md#логика-usereadytablev7jsx));
непрерывность уровней и отсутствие хвостового `;` — как в общем инварианте стадии `[1]`.

## Буквальный эталон (заполняется при первом заведомо-исправном прогоне)

> ⚠ Точная строка grep-запроса зависит от declension-таблиц `theGroups` внутри
> `ForIndex.jsxinc` и **воспроизводима только прогоном в InDesign** (автономно скрипт не
> запускается). Поэтому буквальный снимок ниже заполняет оператор при первом прогоне на
> **заведомо исправной** версии `UseReadyTable.v.7.jsx` (текущая, после видео 18), после чего
> будущие прогоны сверяются с ним построчно.

| Строка | Термин | Ожидаемый grep-запрос (буквально) |
|---|---|---|
| L1 | `ними` | _(вставить из первого исправного прогона)_ |
| L2 | `кха-тха` | _(вставить)_ |
| L3 | `ом` | _(вставить)_ |
| L4 | `супруг…` | _(вставить)_ |

Как заполнить: прогнать дрилл на текущей v7 → скопировать содержимое третьей колонки
`IndexList` по строкам L1–L4 → вставить сюда → закоммитить как замороженный базовый снимок.
После этого регресс = любое расхождение с этой таблицей на строках L1–L3.

## Как сверять

1. Открыть `Golden Fish.idml`, добавить строки-ловушки L1–L4 в стартовый `IndexList`.
2. Прогнать `UseReadyTable.v.7.jsx`.
3. Для L1–L3 выполнить `ShowFoundByGrep.v.3.jsx` по строке — запрос **обязан** находить свою
   форму в учебном тексте. Пустой результат на L1 = регресс дефекта «одной формы».
4. Сверить буквальные запросы с таблицей выше (когда она заполнена). Любое расхождение на
   L1–L3 → **не выпускать** обновлённый скрипт в реальный прогон, разобрать причину.
